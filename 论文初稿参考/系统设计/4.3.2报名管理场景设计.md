# 4.3.2 报名管理场景设计

### 1. 静态结构设计

报名管理场景涉及报名实体类（Registration）、用户实体类（User）、活动实体类（Activity）三个核心实体，类图如图4-3所示。

**【类图结构（供绘制参考）】**

```
┌─────────────────────────┐          ┌─────────────────────────┐
│      User（用户）        │          │   Activity（活动）       │
├─────────────────────────┤          ├─────────────────────────┤
│ - id: Long              │          │ - id: Long              │
│ - nickname: String      │          │ - title: String         │
└───────────┬─────────────┘          │ - maxParticipants: Int  │
            │ 1                      │ - currentParticipants   │
            │ 提交                    │ - deadline: DateTime    │
            ▼ *                      └───────────▲─────────────┘
┌─────────────────────────┐                      │ 1
│  Registration（报名）    │                      │ 关联
├─────────────────────────┤                      │
│ - id: Long              │                      │ *
│ - userId: Long          │──────────────────────┘
│ - activityId: Long      │
│ - status: Integer       │
│ - queueNumber: Integer  │
│ - emergencyContact      │
│ - emergencyPhone        │
└─────────────────────────┘
```

**实体类说明**：

**报名实体类（Registration）**：存储报名记录的完整信息，包括报名ID、用户ID、活动ID、报名状态、候补排队号、报名备注、紧急联系人姓名、紧急联系人电话、审核人ID、审核时间、取消时间、创建时间等属性。

**用户实体类（User）**：存储用户信息，在报名管理场景中用于标识报名用户和验证用户身份。

**活动实体类（Activity）**：存储活动信息，报名时需要验证活动状态、报名截止时间和容量。

**类关系说明**：一个用户实体类（User）可以提交多个报名实体类（Registration），每个报名实体类（Registration）关联一个活动实体类（Activity），活动实体类（Activity）通过当前参与人数字段维护报名人数统计。

### 2. 动态行为设计

**（1）时序图描述**

提交报名申请的时序流程如下：用户在前端点击报名按钮，填写紧急联系人等信息后，React组件进行表单校验；校验通过后，前端向Controller发送POST请求，请求中携带JWT Token；Controller进行JWT认证和参数校验后，调用Service层的submitRegistration方法；Service层首先通过Mapper校验用户是否存在，然后校验活动状态是否为已发布或进行中，接着校验当前时间是否在报名截止时间之前，再校验用户是否已经报名过该活动；校验通过后，Service层查询活动当前参与人数和最大人数，判断是否已满，若未满则设置状态为待审核（status=0），若已满则设置状态为候补（status=3）并分配排队号；最后通过Mapper将报名记录插入MySQL数据库，返回报名ID给前端。

**（2）状态流转**

报名实体在整个生命周期中经历以下状态流转：待审核状态（PENDING，值为0）表示报名申请已提交，等待组织者审核；已通过状态（APPROVED，值为1）表示报名审核通过，用户可参与活动和签到；已驳回状态（REJECTED，值为2）表示报名被组织者拒绝；候补状态（WAITING，值为3）表示活动名额已满，用户进入候补队列；已取消状态（CANCELLED，值为4）表示用户主动取消报名；缺席状态（ABSENT，值为5）表示用户未参加活动。

**（3）异常处理**

报名场景的异常处理包括：活动不存在或未发布时，返回"活动不存在或未发布"错误提示；当前时间超过报名截止时间时，返回"报名已截止"错误提示；用户已存在有效报名记录时，返回"您已报名该活动"错误提示；紧急联系人信息未填写时，返回"请填写紧急联系人信息"错误提示。

### 3. 接口设计

报名管理场景涉及的主要接口如下表所示：

| 接口名称 | 接口描述 | 使用说明 | 使用举例 |
| :--- | :--- | :--- | :--- |
| submitRegistration | 用户填写紧急联系人等信息后提交报名申请，系统创建报名记录 | 请求方式为POST，路径为/api/registrations，需携带JWT Token认证 | POST /api/registrations，请求体包含activityId、emergencyContactName、emergencyContactPhone等字段 |
| auditRegistration | 组织者审核报名申请，可选择通过或驳回 | 请求方式为PUT，路径为/api/registrations/{id}/audit，仅活动组织者或管理员可调用 | PUT /api/registrations/1/audit，请求体包含approved=true |
| cancelRegistration | 用户主动取消自己的报名记录 | 请求方式为PUT，路径为/api/registrations/{id}/cancel，仅报名者本人可调用 | PUT /api/registrations/1/cancel |
| getMyRegistrations | 查询当前用户的所有报名记录，支持按状态筛选 | 请求方式为GET，路径为/api/user/registrations，需携带JWT Token认证 | GET /api/user/registrations?status=1 |
